# Local release guide

GitHub Actions is not used for launcher releases.

The release is built locally. The person building the release does not need
write access to the R2 server. The Linux and macOS release scripts generate all
package and signed update files locally; the finished R2 files can then be
handed to the person who has server access.

## 1. Build the Linux release

Set the update-signing key and run the Linux release builder:

```bash
export SOA_UPDATE_SIGNING_KEY="$HOME/private/soa-update-key.pem"
./packaging/linux/build-release-linux-local.sh
```

The Linux release builder runs the tests, performs the release portability
checks, builds the AppImage, and generates the signed update metadata.

For version `1.0.1`, the relevant output is:

```text
packaging/linux/Story_Of_Alicia-1.0.1-x86_64.AppImage
packaging/linux/manifest.json
packaging/linux/manifest.json.seal
packaging/linux/versions.json
packaging/linux/versions.json.seal
```

## 2. Build the macOS release

On the Mac configured for Developer ID signing and notarization, set the update
signing key together with the Apple credentials described in `SIGNING.md`, then
run:

```bash
export SOA_UPDATE_SIGNING_KEY="$HOME/private/soa-update-key.pem"
./packaging/macos/build-release-macos-local.sh
```

The macOS release builder builds and tests the app, signs and notarizes it,
creates and verifies the DMG, and generates the signed update metadata.

For version `1.0.1`, the relevant output is:

```text
build-macos-release-local/Story_Of_Alicia-1.0.1-macos.dmg
packaging/macos/manifest.json
packaging/macos/manifest.json.seal
packaging/macos/versions.json
packaging/macos/versions.json.seal
```

## 3. How `versions.json` is generated

Do not build `versions.json` by hand.

Before generating a new history file, each metadata generator checks the
existing signed `versions.json` from:

```text
https://r2.storyofalicia.com/launcher/<platform>/versions.json
```

and the `launcher-updates` fallback branch:

```text
https://raw.githubusercontent.com/Story-Of-Alicia/soa-launcher-qt/launcher-updates/<platform>/versions.json
```

The corresponding `.seal` is fetched and verified as well.

If both remote copies are available, they must agree. If one endpoint is
unavailable, the valid copy from the other endpoint can be used. If neither has
history yet, the generator treats it as the first release.

The new release is merged into the verified history and only the newest three
versions are retained.

## 4. Create the GitHub release

Both platform manifests must describe the same launcher version before anything
is published.

Tag the exact commit used for the release:

```bash
git tag -a v1.0.1 -m "Story of Alicia Launcher 1.0.1"
git push origin v1.0.1
```

Create the GitHub Release with only the two user-facing packages:

```bash
gh release create v1.0.1 \
  packaging/linux/Story_Of_Alicia-1.0.1-x86_64.AppImage \
  build-macos-release-local/Story_Of_Alicia-1.0.1-macos.dmg \
  --repo Story-Of-Alicia/soa-launcher-qt \
  --verify-tag \
  --title v1.0.1 \
  --generate-notes
```

If the GitHub Release already exists, upload or replace the two package files:

```bash
gh release upload v1.0.1 \
  packaging/linux/Story_Of_Alicia-1.0.1-x86_64.AppImage \
  build-macos-release-local/Story_Of_Alicia-1.0.1-macos.dmg \
  --repo Story-Of-Alicia/soa-launcher-qt \
  --clobber
```

Do not upload update metadata as GitHub Release assets. The release should only
show the AppImage and DMG as custom downloadable assets. GitHub may also show
its automatically generated source archives.

## 5. Update the `launcher-updates` branch

The fallback branch contains only signed update metadata:

```text
linux/manifest.json
linux/manifest.json.seal
linux/versions.json
linux/versions.json.seal
macos/manifest.json
macos/manifest.json.seal
macos/versions.json
macos/versions.json.seal
```

Check out or clone the `launcher-updates` branch and replace those eight files
with the files generated by the two release builders.

For example, using a temporary clone:

```bash
tmp="$(mktemp -d)"
gh repo clone Story-Of-Alicia/soa-launcher-qt "$tmp" -- \
  --branch launcher-updates \
  --single-branch \
  --depth 1

mkdir -p "$tmp/linux" "$tmp/macos"

cp packaging/linux/manifest.json \
   packaging/linux/manifest.json.seal \
   packaging/linux/versions.json \
   packaging/linux/versions.json.seal \
   "$tmp/linux/"

cp packaging/macos/manifest.json \
   packaging/macos/manifest.json.seal \
   packaging/macos/versions.json \
   packaging/macos/versions.json.seal \
   "$tmp/macos/"

git -C "$tmp" add linux macos
git -C "$tmp" commit -m "Update launcher metadata for v1.0.1"
git -C "$tmp" push origin launcher-updates
rm -rf "$tmp"
```

The branch does not contain AppImages, DMGs, signing keys, or source code.

## 6. Prepare the server handoff

The person with R2 access needs the two packages and the eight signed metadata
files. No private signing key is needed for uploading because all signing has
already been completed locally.

For version `1.0.1`, hand over:

```text
Story_Of_Alicia-1.0.1-x86_64.AppImage
Story_Of_Alicia-1.0.1-macos.dmg

linux/manifest.json
linux/manifest.json.seal
linux/versions.json
linux/versions.json.seal

macos/manifest.json
macos/manifest.json.seal
macos/versions.json
macos/versions.json.seal
```

The versioned package filenames must not be renamed. Older versioned packages
must remain available because entries retained in `versions.json` point to
their exact package filenames.

Your release work is complete once the GitHub Release and `launcher-updates`
branch are updated and the R2 handoff files have been provided to the server
maintainer.
